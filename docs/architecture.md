# 架构决策记录

这份文档记录「为什么不做什么」，而不只是「做了什么」。

新技术不是免费的：每引入一个中间件，就多一个要部署、要监控、要排查的组件。
对一个还在找产品市场匹配的项目，最贵的不是服务器，是注意力。
所以这里每个决定都写清触发条件——到了那个条件再做，没到就先别碰。

最后更新：2026-11-23

---

## 一、现状：用数字说话

| 维度 | 当前值 | 来源 |
| --- | --- | --- |
| 形态 | 单体 FastAPI，92 个路由 | `grep -c "@router"`（2026-11-23） |
| 进程 | `uvicorn --workers 1` | `backend/entrypoint.sh` |
| 副本 | `numReplicas: 1` | `railway.json` |
| 中间件 | 无 Redis、无消息队列、无 Celery | `requirements.txt` 无相关依赖 |
| 服务端处理耗时 | 10~20 ms | 同连接对比 404 与查库接口 |
| 网络往返 | 约 540 ms | 静态 1KB 文件与空接口同耗时 |
| 单次 Agent 对话模型调用 | **1 次** | `agent_chat.py` 仅一处 `ainvoke` |
| 向量化 | 本地 BGE-M3，CPU 推理，每进程一份 | `EMBEDDING_PROVIDER=local` |

**最关键的一个数字**：单次对话只调 1 次模型。很多 Agent 实现会调 3~5 次
（规划 → 选工具 → 生成 → 校验），那才是成本黑洞。这里没走那条路——
读工具在服务端先执行，结果直接拼进 prompt，模型只负责说人话。

## 二、为什么不拆微服务

微服务解决的是**组织问题**：多个团队改同一份代码互相阻塞、某个模块需要独立扩缩容。
它的代价是网络调用、分布式事务、链路追踪、服务发现、配置中心。

这个项目的现实是：

1. **单人/小团队**。没有「多个团队互相阻塞」这回事，拆了只会让自己维护五套部署。
2. **服务端已经只要 10~20 ms**。一次请求变 5 次服务间调用，每次都加网络开销，
   而网络往返本身就是 540 ms 的大头——拆开只会更慢。
3. **没有任何一个模块需要独立扩缩容**。所有模块的负载都跟着同一个用户行为走。
4. **拆开不会让模型变快**。延迟的大头在供应商那边，不在自己的代码组织方式。

**结论：不拆。** 但保留拆的可能性——按领域分目录（`api/` / `services/` / `agents/` /
`models/`），未来真要拆时是「搬目录 + 加一层 HTTP」，不是「重写」。

这是现在唯一值得为微服务做的事，成本为零。

## 三、技术引入的触发条件

| 技术 | 现在用吗 | 触发条件 | 解决什么问题 |
| --- | --- | --- | --- |
| 微服务 | 不用 | 多个团队需要独立发布 | 组织协作，不是性能 |
| 分布式系统 | 不用刻意做 | 加第二个副本那一刻被动发生 | 状态外置的必然结果 |
| Redis | 暂时不用 | 要加副本时 | 限流窗口、缓存需要跨进程共享 |
| 消息队列 | 不用 | 出现批量异步任务 | 请求不必同步等结果 |
| CDN | 建议做 | 有国内用户时 | 540 ms 往返靠它解决 |
| 读写分离 | 不用 | 单库写入成为瓶颈 | 读多写少且数据量大 |

**关于 Redis**：现在单副本，进程内缓存比 Redis 快（少一次网络往返）。
提前上 Redis 是负优化——多一个组件、多一次网络、多一个故障点，换来的
「可扩展性」在当前规模下用不上。

**关于消息队列**：`reminder_scheduler.py` 里已经写明了取舍——为了一个每天跑几次的
任务引入 broker 不划算，asyncio 循环足够，而且幂等靠数据库唯一约束
（`dedupe_key`）而不是内存标记，进程重启也不丢。真正需要队列的只有两类场景：
批量生成几百份学情报告、大文件解析。现在一个都没有。

**关于分布式系统**：它不是一种「选型」，而是「多副本」的必然结果。一旦有两个进程，
限流窗口、缓存、信号量就必须外置，那时你就在做分布式了——被动发生，不需要主动设计。

## 四、真实的性能瓶颈在哪

### 4.1 延迟：不是代码慢

同一连接上实测（排除握手摊销）：

| 请求 | 耗时 | 说明 |
| --- | --- | --- |
| 静态 1 KB 文件 | 546 ms | 几乎全是网络 |
| 404 空接口 | 539 ms | 服务端几乎没干活 |
| 真正查库的接口 | 556 ms | 只比 404 多 17 ms |

三者几乎一样，说明**服务端处理只占 10~20 ms，其余是物理距离**。
新连接还要额外付约 992 ms 的 TLS 握手，所以第一次测每个请求都显示 1.6 秒。

推论：优化 SQL、加缓存对「打开页面慢」基本无用。要动的是**部署位置、连接复用、
传输体积**。

### 4.2 吞吐：瓶颈在供应商，不在服务器

按 1000 个活跃用户、每人每天 30 次配额估算：

```
日对话量        30000 次
集中在晚上 4 小时  2.1 QPS
再乘峰值系数 3     6.2 QPS
```

两个天花板对比：

| 层 | 上限 | 依据 |
| --- | --- | --- |
| 模型并发闸门 | **6.7 QPS** | 20 路并发 ÷ 每次约 3 秒 |
| Web 单进程（异步 IO） | 100+ QPS | I/O 密集型，保守估计 |

**Web 层有 15 倍余量。** 加副本、上微服务都不会提升吞吐，因为瓶颈在
`LLM_MAX_CONCURRENCY` 和供应商额度，不在自己的服务器。

### 4.3 用户变多，先出问题的是账单不是服务器

一次对话 1 次模型调用，但配额只按**次数**计。同一「1 次」，
长简历润色可能是 3000 prompt tokens，短问答可能只有 300——成本差十倍。

不知道 token 就无法定价、无法判断哪个用户是亏的。
所以计量 token 比加副本优先得多（已于 2026-11-23 补上，见 `services/llm_usage.py`）。

## 五、加副本的前置条件

加副本不是改一个数字，下面这些进程内状态必须先外置：

| 状态 | 位置 | 多副本后果 |
| --- | --- | --- |
| 限流滑动窗口 | `core/rate_limit.py` | 每个副本各算一套，实际限额变成 N 倍 |
| 仪表盘推荐缓存 | `api/endpoints.py` | 命中率降到 1/N，模型调用变多 |
| 模型并发信号量 | `services/llm_gate.py` | 实际并发变成 N × 20，直接打爆供应商额度 |
| WebRTC 调用日志 | `api/webrtc_agent.py` | 各副本只看到自己那份 |
| **BGE-M3 向量模型** | `services/embedding.py` | **每副本加载一份 1~2 GB，内存与 CPU 成本翻 N 倍** |

前四个换成 Redis 就解决。**embedding 是硬骨头**：本地 CPU 推理，
3 个副本就是 3 份模型 + 3 份 CPU 争抢，Railway 上成本直接翻三倍，推理还更慢。

所以正确顺序是：

```
embedding 拆成独立服务或换 API  →  Redis 接管限流与缓存  →  才谈 numReplicas > 1
```

顺序反了会白花钱：先加副本，然后发现内存爆了、限流失效了、推理更慢了。

## 六、Agent 能力覆盖

已接 7 个页面、14 个工具（L2：读该页数据 + 调该页写接口）：

| 页面 | 工具数 | 说明 |
| --- | --- | --- |
| 简历工作台 | 4 | 读简历、改写、投递准备 |
| 投递看板 | 2 | 读列表、推进状态（写，需确认） |
| 我的计划 | 2 | 读计划、勾选任务（写，需确认） |
| 错题本 | 3 | 读到期待复习、收录错题、标记已解决 |
| 家长门户 | 1 | 只读，学情概览 |
| 知识图谱 | 1 | 只读，薄弱点排序 + 前置链 |
| 仪表盘 | 1 | 只读，跨页聚合「现在最该做的一件事」 |

**还没接的页面，判断如下：**

| 页面 | 建议 | 理由 |
| --- | --- | --- |
| 学习评估 | 值得接 | 有维度得分，能答「哪项弱、怎么练」 |
| AI 学习导师 | **合并而非新增** | 它本身就在调模型，再挂 dock 就是一个页面两个 AI 入口 |
| 知识抽取 | 一般 | 用户动作是「传文件等结果」，对话价值低于按钮 |
| 企业知识库 | 一般 | 检索问答已在页面内 |
| 协作学习 | 暂缓 | 多人共享数据，权限模型没建好会越权 |

**比继续铺页面更值的新功能：**

- **JD 匹配**：粘一段 JD → 对比简历 → 说清缺什么。纯只读，复用现有工具。
- **模拟面试官**：读简历 + 投递记录，多轮追问后给反馈。最像「真需求」的形态。

**一个已知的产品债**：家长页有两个 AI 入口——主体区的旧周报接口
`/agent/parent/stream` 和右下角 dock。它们可能对同一份数据给出不同说法，
应该合并成 dock 一个入口，主体只展示结构化数据。

## 七、三端策略

**现在不做原生 APP。**

Web 已有 PWA manifest 和 Service Worker，能装到桌面和手机主屏，覆盖 APP 八成场景。
原生 APP 的额外收益主要是推送和离线，而这两件事目前都没做（提醒只在本站页面
打开时生效）。

推荐顺序：

1. **Web 打磨**（现在）
2. **小程序轻量版**：只做「查进度 / 看错题」，不做完整对话——流式输出和长文本
   在小程序里体验会打折
3. **Capacitor 套壳**：真需要推送和离线时再考虑，不要从零写原生

## 八、性能优化清单

### 已做（2026-11-23）

| 优化 | 效果 |
| --- | --- |
| argon2 密码哈希移出事件循环 | 事件循环停顿 447 ms → 11 ms |
| 补 `learning_records` / `mistake_records` 复合索引 | 消除全表扫描 |
| 仪表盘推荐改后台生成 | 冷缓存首屏数秒 → 17 ms（本地）/ 461 ms（线上，基本只剩网络） |
| 知识图谱页 g6 动态导入 | 页面分块 1317 kB → 8.9 kB |
| 健康检查改查库 | `/` 返回 index.html 时库挂了也 200，等于没监控 |
| token 计量 | 从「只知次数」到「知道花多少钱」 |

### 待做（按性价比排序）

1. **流式接口的 token 采集已补，但依赖供应商返回 `stream_options`**。
   若换供应商后自检持续报漏记，先查这一项。
2. **找回密码 / 邮箱验证**。忘密码等于直接流失，这是账号体系最基础的缺口。
3. **健康检查之外的监控**：没有错误上报（Sentry）、没有日志聚合、没有告警。
   线上 500 现在只能等用户投诉。
4. **管理后台**。18 个前端页面全是学生端，客服改一个学生数据只能连库。
5. **CDN + 国内机房**。这是唯一能解决 540 ms 往返的手段，但需要域名备案，
   属于产品决策不是技术决策。

## 九、商业化差距（摘要）

详细分析见对话记录，这里只留结论：

| 层 | 状态 |
| --- | --- |
| 合规 | **缺**：无隐私政策、用户协议、注销入口、数据导出、内容审核。面向学生的生成式 AI，这五项在国内是硬要求 |
| 计费 | **假的**：`payment_status="paid"` 是模拟值，订单不校验归属与金额。上线收钱前必须整段重写 |
| 租户配额 | **装饰**：`Tenant` 表有 `token_quota_monthly` / `max_students`，但全项目没有任何一处读取它们 |
| 账号 | 只有邮箱+密码，无找回、无验证、无手机号/微信登录 |
| 监控 | 只有 `/api/health` |
| 规模 | 单副本，加不了副本（见第五节） |
| 工程 | **强项**：CI、81 接口、回归脚本齐全，不是瓶颈 |

**建议顺序：先跑试用拿到「有人愿意用」的证据，再补合规最小集，最后才是交易闭环。**
在拿到付费意愿之前，把支付接得再漂亮都只是给未验证的产品加杠杆。

合规是例外——它不是增长手段，是准入门槛，可以现在就补最小集。
